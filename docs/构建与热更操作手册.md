## 二、发版构建流程（新版 APK）

### 2.1 构建前检查

1. 起始场景必须是 loading：
   - `client/settings/builder.json` 的 `startScene` = `17f52cf1-e57d-4777-b520-afc4f7482a8b`
   - `client/settings/project.json` 的 `start-scene` 同上
   - 注意：`builder.json` 里还有个没被使用的旧键 `start-scene`（仍指向 login），**不用管它**，构建实际取 `startScene`。
2. 客户端版本号（如需）与远端热更版本号的关系见 [4.6 版本号红线](#46-版本号红线必看)。
3. 确认没有把 `.fire`、`.meta` 之类文件手工改坏（`.fire` 一律在 Creator 里改）。

### 2.2 Creator 构建

在 Cocos Creator 里构建 Android（`jsb-link`），输出目录 `client/build/jsb-link`。

### 2.3 产物自检（**必做，别跳**）

```powershell
# 1) 新的 main 包与 settings 是否生成
Get-ChildItem client\build\jsb-link\assets\main | Select-Object Name,Length,LastWriteTime
Get-ChildItem client\build\jsb-link\src | Select-Object Name,Length,LastWriteTime

# 2) 起始场景是否正确（应显示 launchScene:"db://assets/module/loading/loading.fire"）
Get-ChildItem "client\build\jsb-link\js backups (useful for debugging)" -Filter "settings.*.js" |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1 |
  ForEach-Object { Get-Content $_.FullName -Raw }
```

`settings.<hash>.js` 里的 `bundleVers.main` 就是本次构建的主包 hash，等于 `assets/main/index.<hash>.jsc` 的 `<hash>`。这个值同时是**热更指纹**，换包必变。

```powershell
# 3) 用明文调试备份确认代码改动真的进包了（.jsc 是加密的，只能看这个）
$js = Get-ChildItem "client\build\jsb-link\js backups (useful for debugging)" -Filter "main.index.*.js" |
      Sort-Object LastWriteTime -Descending | Select-Object -First 1
$s = Get-Content $js.FullName -Raw
"file=" + $js.Name
"关键字命中: " + ([regex]::Matches($s,"要确认的代码关键字")).Count
```

### 2.4 同步到 CI 打包目录

`jsb-link` 是 Creator 输出，`jsb-default` 才是 CI 编译目录，必须同步：

```powershell
$src="d:\baobao_game\client\build\jsb-link"
$dst="d:\baobao_game\client\build\jsb-default"
foreach($d in @("assets","src","jsb-adapter","js backups (useful for debugging)")){
  robocopy "$src\$d" "$dst\$d" /MIR /NFL /NDL /NJH /NJS /NP
}
foreach($f in @("main.js","project.json","cocos-project-template.json",".cocos-project.json")){
  Copy-Item "$src\$f" "$dst\$f" -Force
}
```

- `robocopy /MIR` 会删除目标里多余文件，属正常。
- **绝对不要动 `jsb-default/frameworks/`**（引擎与 Android 工程，CI 直接用）。
- `robocopy` 退出码 1 表示“成功复制”，PowerShell 可能显示为失败，忽略即可。

**同步后必须给 `main.js` 打热更启动补丁**（幂等，重复执行只提示跳过）：

```powershell
node tools/patch_main_boot.js client/build/jsb-link
node tools/patch_main_boot.js client/build/jsb-default
```

**为什么要打**：`main.js` 里写死了 `require('src/settings.f20d1.js')`、`cocos2d-jsb.8491d.js` 这类带构建哈希的文件名，每次构建都变。旧包里加载的永远是包内那份 settings，于是 `bundleVers` 还是老值，热更下来的新主包 `assets/main/index.<新hash>.jsc` 永远不会被使用。补丁把 require 改成“先到热更目录的 `project.manifest` 里找本次构建真实的 src 文件名，找不到再回退包内名字”。

### 2.5 重新生成热更清单

```powershell
node tools/gen_manifest.js client/build/jsb-default 1.0.10 http://47.239.100.68:9100/hotupdate
```

输出应为：

```
版本 1.0.10 资源 3046 个
project.manifest: client\build\jsb-default\project.manifest
version.manifest: client\build\jsb-default\version.manifest
```

**为什么必须跑**：Creator 在 md5Cache 下有时不重写清单（或写成上一版的），会出现清单里的文件名与实际产物对不上，热更漏下/错下文件。这个脚本按磁盘真实文件重算 md5。

清单现在覆盖三个目录（原来是只有 `assets/`）：

| 目录 | 内容 | 不覆盖的后果 |
|---|---|---|
| `assets/` | 主包 `index.<hash>.jsc`、config、场景资源 | 代码/资源永远不更新 |
| `src/` | `settings.<hash>.jsc`、`cocos2d-jsb.<hash>.jsc`、`physics.<hash>.jsc` | settings 不更新 → 仍加载旧主包 |
| `jsb-adapter/` | `jsb-engine.js`、`jsb-builtin.js` | 适配层无法热更 |

`frameworks/`（原生库）不在清单内，那部分只能重新打 APK。

校验清单：

```powershell
$m = Get-Content client\build\jsb-default\project.manifest -Raw | ConvertFrom-Json
$m.version
$m.assets.PSObject.Properties.Name | Where-Object { $_ -like "assets/main/index*" -or $_ -like "src/*" -or $_ -like "jsb-adapter/*" }
```

### 2.6 提交并推送

```powershell
git add "client/assets/module/..." "client/build/jsb-default" "client/build/jsb-link"
git commit -F "$env:TEMP\commit_msg.txt"   # PowerShell 5 不支持 heredoc，消息写文件
git push origin main
```

推送后 Actions 自动打包，构建完成后到 Actions 页面下载 artifact `SCMJ-android-signed`。

### 2.7 安装

- 新包签名固定（`.github/signing/scmj.jks`），可直接覆盖安装，无需卸载。
- 若手机里装的是**同一版本号但代码已坏**的包（例如本次 `retain` 崩溃包），只能装新 APK，热更救不了（见 4.7）。

## 三、构建 / 环境注意事项（都是踩过的坑）

1. **`.jsc` 是加密产物**（`encryptJs: true` + `xxteaKey`），不能手改，也不能用明文 JS 替换；只能 Creator 重新构建。因此“改了代码但没重新构建”等于没改。
2. **`jsb-link` ≠ 打包目录**：CI 只编译 `jsb-default`，不同步就等于发旧包。
3. **起始场景双入口**：原生环境下 `login.js` 有“未检查过热更就 loadScene('loading')”的守卫，loading 场景加载结束再进 login。改启动逻辑时不要破坏这个顺序，否则 loading/login 会重叠闪烁。
4. **PowerShell 5 限制**：不支持 `&&`、不支持 heredoc；多命令用 `;`，提交信息用 `git commit -F 文件`。
5. **`.fire` 不要手改**：Creator 保存会重排 `__id__`，diff 看起来巨大但语义正确；手改极易造成场景损坏。
6. **`jsb-default/frameworks/` 不要覆盖**：`jsb-link` 的 `settings.gradle` 含 `:instantapp` 模块，本地 gradle 会失败；CI 用的是 `jsb-default`，其 gradle 已清理好。
7. **gradle 文件写入必须无 BOM**：PowerShell `Set-Content` 默认带 BOM 会让 gradle 解析失败（如需改 gradle 用 UTF8 无 BOM）。
8. **构建前不要相信“上次也是这样”**：每次发版都跑一遍 2.3 的自检，确认新 hash 与新代码都在包里。

## 四、APP 热更新

### 4.1 链路总览

```
APK 内置 project.manifest(1.0.10)
        │ 启动 loading 场景
        ▼
Lodinglogin.onLoad → applyHotUpdateSearchPaths()  ← 恢复上次热更路径（带指纹校验）
        │
        ▼
Lodinglogin.start → checkHotUpdate()
        │  new jsb.AssetsManager("project.manifest", storagePath, compareVersion)
        ▼
读取本地清单 → 比较 remoteManifestUrl(服务器) 清单版本
        │
        ├─ 远端不新 / 清单异常 / 超时15s → 跳过热更 → checkVersion → 预载 → login
        └─ 远端更新 → update() 下载全部差异资源 → UPDATE_FINISHED
                    → 保存路径+指纹 → cc.game.restart() 一次
```

关键代码：`client/assets/module/loading/script/Lodinglogin.js`
- `HOT_UPDATE_ENABLED = true`：热更总开关
- `compareVersion`：数字逐段比较（引擎默认按字符串比较，会把 `1.0.9` 判成比 `1.0.10` 大，导致死循环）
- `_buildStamp()`：取 `cc.assetManager.bundleVers` 作为构建指纹（`main.js` 会清空 `window._CCSettings`，不能用它）
- 热更资源目录：`jsb.fileUtils.getWritablePath() + "baobao_hotupdate/"`

### 4.2 启动时判定顺序（`applyHotUpdateSearchPaths`）

1. 没有 `HotUpdateSearchPaths` → 不处理，正常启动。
2. 当前 `getSearchPaths()` 已经等于记录值 → 说明已生效，不重启。
3. **构建指纹不一致**（装了新 APK）→ 旧热更一律作废：清 localStorage + 删热更目录，正常启动。
4. 热更目录实际不存在 → 作废记录，正常启动。
5. 通过 → `setSearchPaths()`，若 `HotUpdateAppliedPaths` 已等于该组路径则不再重启；否则写标记并 `cc.game.restart()` **一次**。

> 历史上“页面一直闪”就是这套流程失控造成的：重启后标记丢失 → 又判断不一致 → 再重启。现在所有跨重启状态都存 `localStorage`，且同一组路径只重启一次。

### 4.3 localStorage 键

| 键 | 作用 |
| --- | --- |
| `HotUpdateSearchPaths` | `{paths:[...]}` 热更资源搜索路径 |
| `HotUpdateAppliedPaths` | 已为哪组路径重启过（防重复重启） |
| `HotUpdateBuildStamp` | 下载该热更的 APK 构建指纹（换包作废旧热更） |

用户端清数据（或卸载重装）会清空这些键，客户端回到 APK 内置版本。

### 4.4 事件处理

| 事件码 | 处理 |
| --- | --- |
| `ERROR_NO_LOCAL_MANIFEST` / `ERROR_DOWNLOAD_MANIFEST` / `ERROR_PARSE_MANIFEST` | 跳过热更，继续启动 |
| `ALREADY_UP_TO_DATE` | 跳过热更，继续启动 |
| `NEW_VERSION_FOUND` | 开始 `update()` 下载 |
| `UPDATE_PROGRESSION` | 更新进度条 |
| `UPDATE_FINISHED` | 保存路径 + 指纹 → `cc.game.restart()` |
| `UPDATE_FAILED` | `downloadFailedAssets()` 重试，累计 >3 次跳过热更 |
| `ERROR_UPDATING` / `ERROR_DECOMPRESS` | 累计 >3 次跳过热更 |

另有 15 秒检查看门狗：服务器不可达时自动跳过热更继续启动，不会卡在“检查更新”。

### 4.5 发布热更（管理后台）

1. 在 Creator 里构建（输出 `jsb-link`），同步到 `jsb-default`（步骤 2.4）。
2. 用 `tools/gen_manifest.js` 生成清单，**版本号必须比现有 APK 内置清单高**（如 APK 是 `1.0.10`，热更就用 `1.0.11`）：
   ```powershell
   node tools/gen_manifest.js client/build/jsb-default 1.0.11 http://47.239.100.68:9100/hotupdate
   ```
3. 把 `client/build/jsb-default` 目录压成 zip（zip 根目录或单层子目录里必须含 `project.manifest`、`version.manifest`）。
4. 打开管理后台（超级管理员），进入热更区域上传该 zip → “发布热更”。
   - 接口：`POST /admin/hotupdate/upload`（服务端解压校验后**原子替换** `account_server/hotupdate`，旧目录先改名 `hotupdate_bak`）
   - 也可手工把文件放到服务器 `account_server/hotupdate/`，效果一样。
5. 手机**冷启动** APP：检查更新 → 下载 → 自动重启一次 → 新资源生效。

注意：
- 清单里 `packageUrl` 必须是公网地址 `http://47.239.100.68:9100/hotupdate`。写成 `127.0.0.1/localhost` 时服务端会自动改成公网，但最好一开始就写对。
- 热更包包含 `assets/main/index.<hash>.jsc`，所以**纯 JS 改动可以靠热更下发**，不用重装 APK。
- 热更下载的是全量差异，首次发布体积较大，尽量在空闲时段操作。

### 4.6 版本号红线（必看）

CI 里 `gen_manifest` 的 APK 版本号是**写死**在 `.github/workflows/build-native.yml`（当前 `1.0.10`）。

推论：如果远端热更清单版本（如 `1.0.11`）高于新 APK 内置清单版本（`1.0.10`），**新装的 APK 一启动就会去下载那份热更**，用旧构建的代码覆盖新包，出现“装新包反而倒退”的诡异现象（构建指纹只能挡住“曾经热更过”的老用户，挡不住全新安装）。

铁律：

- 发新 APK：要么先把远端热更版本降到 ≤ APK 版本（或清空 `hotupdate` 目录），要么同步把 CI 里的 APK 版本号改成 ≥ 远端热更版本。
- 热更只改 `client/build/jsb-default` 的产物与服务器清单，**不重新打 APK**。

### 4.7 热更救不了的情况

热更入口本身在 APK 内置 JS 里。如果内置 JS 一启动就抛异常（如本次 `jsb.AssetsManager.retain is not a function`），连“检查更新”都执行不到，热更无从下手——只能重新打 APK。因此**改热更/启动代码后必须真机验证一次**，别只看代码。

### 4.8 热更为什么之前下发无效（已修）

原来只有两处缺口，导致下载完也不生效：

1. **`main.js` 写死带哈希的 src 文件名**：`require('src/settings.f20d1.js')`。旧包永远加载包内那份 settings，`bundleVers` 是老值，引擎就去加载 `assets/main/index.<旧hash>.jsc`。新下载的 `index.<新hash>.jsc` 躺在热更目录里没人用。
2. **清单只收 `assets/`**：`src/settings.*`、`src/cocos2d-jsb.*`、`src/physics.*`、`jsb-adapter/*` 根本不会被下载。

修法：

- `tools/gen_manifest.js` 现在收集 `assets/ + src/ + jsb-adapter/`；
- `tools/patch_main_boot.js` 给 `main.js` 打补丁：启动时先在热更目录的 `project.manifest` 里找本次构建真实的 `src/settings.*.jsc` 等文件名，存在就 `require` 它，找不到才回退包内名字；
- 补丁已应用到当前 `jsb-link` / `jsb-default` 的 `main.js`。

生效前提：**必须有一版带补丁的 APK 先装到设备上**。旧 APK 的 `main.js` 没有这个逻辑，再怎么发热更也不会用新代码。之后：

1. 改代码 → Creator 构建 → 同步 `jsb-default` → 打补丁 → `gen_manifest` 出新版本号
2. 上传 zip 到服务器 `hotupdate/`
3. 手机冷启动：检查更新 → 下载 → 自动重启一次 → 新代码生效

Android 与 iOS 走的是同一套 JSB 机制（`jsb.fileUtils.setSearchPaths` + `cc.game.restart()`），`jsb-default` 一份产物两端通用；iOS 只需在发版时同步构建一次，之后的代码改动同样可以热更。

判断是否真的用上了新代码，看启动日志：

```
[HotUpdate] 已恢复热更搜索路径, 重启生效
```

重启后 settings 里的 bundleVers 应该已经变成新构建的哈希（可在 `cc.assetManager.bundleVers` 打印确认）。

## 五、服务器（宝塔）部署与重启

### 5.1 结构

```
/www/wwwroot/baobao/
├── configs/                 # 服务端配置
├── account_server/          # 端口 9100（含 hotupdate/ 静态目录、admin 后台）
├── hall_server/             # 端口 9101
├── game_server/             # 端口 10100
└── server/logs/             # 运行日志
```

进程由 **systemd** 托管（`/etc/systemd/system/` 下，均已 `enabled`）：

| 服务单元 | 目录 | 端口 |
|---|---|---|
| `baobao-account.service` | account_server | 9100 |
| `baobao-hall.service` | hall_server | 9101 |
| `baobao-game.service` | game_server | 10100（另监听 9103） |

本地改动 → 同步到 `server_deploy/`（部署快照）→ 上传覆盖服务器对应目录。**改完必须重启对应服务才生效**（Node 不热加载）。

> 不要再用 `nohup node app.js ../configs` 手动起服务。手动起的进程不在 systemd 的 cgroup 里，会和 service 抢端口：service 起不来 → 自动重启 → 出现多个 node 进程，还可能互相抢房间状态。

### 5.2 重启服务（改代码后）

```bash
# 只重启改到的服务（最常用）
systemctl restart baobao-game

# 三个一起重启（改了 utils/db.js 等共用文件时必须三个都重启）
systemctl restart baobao-account baobao-hall baobao-game
```

校验：

```bash
systemctl status baobao-account baobao-hall baobao-game --no-pager | grep -E "●|Active:|Main PID"
ss -lntp | grep -E "9100|9101|10100|9103"
```

判断标准：
- 三个 service 都是 `Active: active (running)`；
- `ss` 里 9100 / 9101 / 10100 / 9103 各自归属一个 PID，且等于对应 service 的 Main PID；
- 进程数与归属：`for p in $(pgrep -f "node app.js"); do echo "$p $(cat /proc/$p/cgroup | sed 's/.*\///')"; done` 应正好 3 行，cgroup 为 `baobao-*.service`。

### 5.2.1 清理历史遗留的手动进程

早期用 `nohup` 起的实例会残留（`PPID=1`、cgroup 为空），表现是“端口被占用、service 起不来、进程越杀越多”：

```bash
systemctl stop baobao-game
# 杀掉不属于 systemd 的残留（按 cwd 判断）
for p in $(pgrep -f "node app.js"); do
  [ "$(readlink /proc/$p/cwd)" = "/www/wwwroot/baobao/game_server" ] && kill -9 "$p"
done
systemctl start baobao-game
```

另外 cron 里还有一条每分钟执行的看门狗：

```
* * * * * /www/wwwroot/baobao/watchdog.sh >/dev/null 2>&1
```

它只按端口探测、不认 systemd，会和 service 的自动重启重复拉起进程。systemd 已经是守护方，建议移除：

```bash
crontab -l | grep -v "watchdog.sh" | crontab -
```

### 5.3 重启宝塔面板 / 整机

```bash
# 只重启宝塔面板（不影响 node 业务进程）
bt restart
# 或
/etc/init.d/bt restart
```

```bash
# 重启整台服务器（会中断所有在线玩家，尽量选低峰）
reboot
```

整机重启后 node 进程由 systemd 自动拉起（三个 unit 都是 `enabled`），用 `systemctl status baobao-account baobao-hall baobao-game` 确认即可。

### 5.4 日志与排错

```bash
# systemd 接管后优先看 journal
journalctl -u baobao-game -n 200 --no-pager
journalctl -u baobao-account -n 200 --no-pager

# 若 unit 里配置了重定向, 日志也在 logs/ 下
tail -n 200 /www/wwwroot/baobao/logs/game_server_stdout.log
tail -n 200 /www/wwwroot/baobao/logs/account_server_stdout.log
```

常见问题：
- 端口被占用起不来 → `ss -lntp | grep 10100` 找到占用 PID；若它不属于 `baobao-game.service`，按 5.2.1 清掉后 `systemctl restart baobao-game`。
- 改了 `gamemgr_*.js` 没生效 → 忘了 `systemctl restart`。
- 出现多个 `node app.js` 进程 → 手动 nohup 实例与 systemd 抢端口，按 5.2.1 处理，并移除 cron 里的 `watchdog.sh`。
- 热更 404 → 确认 `account_server/hotupdate/project.manifest` 存在且 9100 静态托管正常。

## 七、业务侧注意点

1. **老庄提示**：`Seat.setLaoZhuang(count)`，`count >= 1` 时在庄家标下方动态生成“老庄X”。数据来自服务端 `game_start_push.laozhuang`；服务端只在**庄家连庄**时 `laozhuangCount + 1`，所以第一局不会显示，从第二局连庄开始出现。`gamemgr_zjzx.js` 已补 `laozhuang` 字段，**必须重启 game_server 才生效**。
2. **`hupailist` 节点已从 6 个麻将场景移除**（无业务作用），脚本里的 `_hupaiLists` 引用也已清理。Creator 里如果再看到，是内存中的旧场景或旧构建产物，不要重新加回。
3. **结算弹窗 `infoBar/infoLabel`**：已去掉“扣费/倍率”，所有麻将场景统一由 `GameResult.js::setInfoLine` 生成，不要在各场景单独加回。
4. **场景文件 `.fire`** 一律在 Creator 里改；批量脚本改动后必须再跑一次 Creator 构建验证。
